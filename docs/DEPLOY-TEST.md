# Тестовый сервер: первая настройка и развёртывание через GitHub

Схема: вы один раз настраиваете сервер скриптом, кладёте ключ в GitHub Secrets, а дальше проект
обновляется автоматически (GitHub Actions копирует файлы по SSH и запускает `deploy.sh`).
Приватный ключ видите только вы. Пароли и ключи в чат не отправляйте.

## 1. Сервер
Закажите сервер: KVM, 2 vCPU, 4 ГБ RAM, 40–50 ГБ SSD, Ubuntu 24.04. Доступ root вам выдаст провайдер.
Проверьте на сервере: `systemd-detect-virt` (должно быть `kvm`), `free -h`, `df -h /`.

## 2. Ключ для развёртывания (на вашем компьютере)
```
ssh-keygen -t ed25519 -f ~/.ssh/quality_deploy -C quality-deploy -N ""
```
Получатся два файла: `quality_deploy` (приватный, никому не отдавать) и `quality_deploy.pub` (публичный).

## 3. Настройка сервера (один раз)
Скопируйте скрипт на сервер (в папке с клоном репозитория, ветка `infra-deploy`):
```
scp infra/server/setup.sh root@IP-СЕРВЕРА:/root/
ssh root@IP-СЕРВЕРА
```
Запуск на сервере. Вариант без домена (для теста по IP):
```
bash setup.sh --pubkey "ssh-ed25519 AAAA...ваш публичный ключ" --no-domain IP-СЕРВЕРА
```
Вариант с доменом (A-записи обоих имён должны указывать на IP сервера до первого развёртывания):
```
bash setup.sh --pubkey "ssh-ed25519 AAAA..." --site-domain test.example.ru --admin-domain admin-test.example.ru
```
Скрипт установит Docker, создаст пользователя `deploy`, включит firewall (22, 80, 443, при `--no-domain` ещё 8081),
добавит swap 2 ГБ, создаст `/opt/quality/.env` со случайными секретами. В конце он напечатает:
- пароль администратора CMS (показывается один раз, сохраните в менеджере паролей);
- строку для `DEPLOY_KNOWN_HOSTS` вида `IP ssh-ed25519 AAAA...`.

## 4. Проверка входа и закрытие пароля
В **втором** окне терминала: `ssh -i ~/.ssh/quality_deploy deploy@IP-СЕРВЕРА`. Если вход работает, в первом окне
(под root) выполните снова `bash setup.sh ... --harden-ssh` с теми же параметрами. Он запретит вход по паролю.
Не закрывайте рабочее окно, пока не проверите вход ещё раз.

## 5. Настройка почты администратора
На сервере отредактируйте `/opt/quality/.env`: замените `ADMIN_EMAIL=admin@example.com` на свой адрес
**до первого развёртывания** (иначе придётся менять в панели).

## 6. Секреты в GitHub
Репозиторий → Settings → Secrets and variables → Actions → New repository secret:

| Имя | Значение |
|---|---|
| `DEPLOY_HOST` | IP сервера (или домен) |
| `DEPLOY_USER` | `deploy` |
| `DEPLOY_SSH_KEY` | содержимое приватного файла `~/.ssh/quality_deploy` целиком |
| `DEPLOY_KNOWN_HOSTS` | строка, которую напечатал `setup.sh` |

## 7. Первое развёртывание
Запушьте ветку `deploy-test` (это сделаю я, когда вы скажете, что секреты добавлены): `git push origin infra-deploy:deploy-test`.
Прогресс: репозиторий → вкладка Actions → «Deploy test». Первый запуск собирает образы (10–15 минут) и сам выполняет первичную загрузку
(схема CMS, роли, услуги). Следующие пуши в `deploy-test` просто обновляют сайт.
Проверка: сайт `http://IP-СЕРВЕРА` (или ваш домен), админ-панель `http://IP-СЕРВЕРА:8081`.

## 8. Сотрудники с TOTP
На сервере под `deploy`:
```
cd /opt/quality
docker compose exec -e PUBLIC_URL=http://localhost:8055 cms node scripts/create-user.mjs ваш@email Администратор
docker compose exec -e PUBLIC_URL=http://localhost:8055 cms node scripts/create-user.mjs редактор@email Редактор
```
Для администратора из `.env` укажите тот же email: команда зададит ему новый пароль и TOTP.

## Отзыв доступа
Удалите секрет `DEPLOY_SSH_KEY` в GitHub и ключ из `/home/deploy/.ssh/authorized_keys` на сервере.
Пользователь `deploy` входит в группу `docker`, а это почти root: ключ нигде, кроме GitHub Secrets и вашего компьютера, не храните.

## Ограничения
- `apply-schema` создаёт только недостающие коллекции, поля существующих коллекций он не меняет. Изменения схемы в будущих релизах будут идти отдельными шагами.
- Первичная загрузка (роли и услуги) выполняется один раз, о чём говорит файл `/opt/quality/.initialized`. Если удалить его и развернуть снова, услуги перезапишутся значениями из `cms/seed/data.json`.
- Резервные копии начнут работать, когда в `.env` заполнены `RESTIC_REPOSITORY` и ключи S3 и настроено расписание (`infra/backup/crontab.example`).
- Образы собираются на самом сервере: на 4 ГБ это работает, но на 2 ГБ без swap сборка Directus может упасть.
